# Phase 5 — переезд на Neon выполнен (9 ноября 2026): как это устроено и как с этим жить

Статус: **игра работает на Neon** (PostgreSQL 18, Франкфурт, план Launch). Firestore остаётся только для аутентификации (Firebase Auth) и как запасной путь отката; правила Firestore заблокированы (`allow read, write: if false`).

## Как устроено

- Единственная точка входа сервера в базу — `admin.firestore()` в `netlify/lib/fb.js`. При `STORE=pg` она заменяется слоем `server/pgdocs.js`: он повторяет API Firestore, а данные лежат в таблице `fs_docs` (`path, parent, coll, id, data jsonb, create_time, update_time`). Игровой код (`saves.js`, `cycle.js`, `gold.js` и т.д.) не менялся.
- Транзакции: PG-транзакция с `pg_advisory_xact_lock` на путь документа и `SELECT ... FOR UPDATE`; запись применяется при коммите; повтор до 12 раз при `40001/40P01/23505`.
- Клиент: `public/js/nfdb.js` имитирует `firebase.firestore()`. Чтение и запись идут через шлюз `server/fsgate.js`: одиночные операции — `POST /api/fs`, подписки — WebSocket-сообщения `fsl/fsu` (ответы `fss` — дельты, `fse` — ошибки). Если сокет недоступен, клиент опрашивает по HTTP раз в 4 с. Права проверяются на сервере (`server/fsrules.js`, порт `firestore.rules`; всё, что не описано, запрещено).
- Подписки на сервере — опрос базы раз в `PG_POLL_MS` (по умолчанию 2000 мс) плюс мгновенный толчок после записи.
- Какой режим включён, клиент узнаёт из `/store.js`: `window.NF_STORE="pg"` или `"fs"` (не кэшируется, service worker его не трогает).
- **Реляционные таблицы (0001–0003, 43 шт.) — это снимок на момент переезда и больше не обновляются.** Источник истины для игры — `fs_docs` (таблица 0004). Реляционные таблицы оставлены для будущего перевода «горячих» данных (кошельки, рынок) на нормальные таблицы; до тех пор на них ничего не опирать.

## Переменные окружения (Fly)

| Имя | Что делает |
|---|---|
| `DATABASE_URL` | pooled-адрес боевой базы Neon (в хосте `-pooler`). Секрет |
| `STORE=pg` | включает Neon. Нет переменной — игра на Firestore |
| `MAINT=1` | техобслуживание: все страницы 503, сокет закрыт, фоновые задачи с записью не стартуют (`/healthz`, `/hubz` отвечают) |
| `PG_POLL_MS` | период опроса подписок (по умолчанию 2000, минимум 300). Больше значение — меньше нагрузка и расход compute, но дольше задержка чата |
| `PG_POOL_MAX` | размер пула (по умолчанию 3; машина Fly 256 МБ) |
| `PG_CONN_TIMEOUT_MS` | таймаут подключения (по умолчанию 5000) |

Секреты GitHub: `NEON_PROD_DATABASE_URL` (direct, без `-pooler`), `NEON_TEST_DATABASE_URL` (тестовая база), `FIREBASE_SERVICE_ACCOUNT`, `FLY_API_TOKEN`. Строки подключения никогда не пишутся в чат, логи и Git. Тестовую базу `Northfall-test` боевому приложению не давать.

## Workflows (GitHub Actions, запуск вручную)

| Workflow | Что делает |
|---|---|
| `Neon prod` | `check` — проверка подключения; `schema` — миграции 0001–0004 на пустой базе; `zz-dry` / `zz-delete` / `saves-orphans` — разовая уборка тестовых сохранений (удаляет только при точном совпадении числа) |
| `Cutover` | `status`, `maint-on`, `import`, `go-live`, `rollback` (см. ниже) |
| `Neon test run` | полный прогон тестов на тестовой базе (`reset=yes` стирает её схему) |
| `Firestore export` | зашифрованная выгрузка Firestore (RSA+AES, ключ дешифровки не в репозитории) |
| `Fly deploy` | выкладка на каждый push в `main` |

## Откат на Firestore

Разовый откат возможен, пока не потеряны данные в Firestore (они заморожены на момент переезда; всё, что игроки сделали после, живёт только в Neon):
1. Запустить `Cutover` → `rollback` (убирает `STORE` и `MAINT`).
2. Вернуть старые правила Firestore в консоли Firebase (Rules → вставить сохранённый файл).
Всё, что игроки сделали после 9.11.2026 16:10 (по Израилю), в Firestore не попадёт. Поэтому откат разумен только в первые часы; потом — чинить на месте.

## Повторный переезд / восстановление

Шаги `Cutover`: `maint-on` → (вручную заблокировать правила Firestore) → `import` (останавливается, если боевая база не пуста) → `go-live`. Для восстановления из резервной копии Neon использовать Instant restore в консоли Neon (Launch — до 7 дней).

## Расходы и наблюдение

- Launch: $0.106 за CU-час, $0.35 за ГБ в месяц, платёж по факту. Минимальный размер 0.25 CU круглосуточно ≈ $19–20 в месяц.
- Scale-to-zero отключён (опрос не даёт базе заснуть). Уведомления о расходах включаются в Billing организации Neon (порог ≈ $30); автоматической остановки по лимиту у Neon пока нет.
- Если расход выше ожидаемого — увеличить `PG_POLL_MS` (4000–5000).

## Что осталось сделать

- Убрать клиентскую запись в Firestore и подключение `firebase-firestore` SDK (после недели стабильной работы). Пока SDK — запасной путь отката.
- Политика удаления аккаунтов: `users.status='deleted'` (анонимизация), а не `DELETE` (внешние ключи; платёжные записи хранить).
- Регулярная зашифрованная выгрузка боевой базы как вторая линия резервных копий.
- Обновить `package-lock.json` (`npm install` на машине владельца и коммит).
- Перевод «горячих» данных на реляционные таблицы — по необходимости, не срочно.
