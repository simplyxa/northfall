# Phase 2B — PostgreSQL API contracts

**Статус:** проектирование по статическому чтению исходного кода. Это не описание уже внедрённого PostgreSQL API. Все новые маршруты и сообщения, помеченные «целевой контракт», пока предлагаемые.

**Ограничения этапа:** Firestore не читался; экспорт не запускался; PostgreSQL не подключён; схема не применялась; рабочие маршруты, WebSocket-протокол, конфигурация и деплой не менялись. Firebase Auth остаётся источником аутентификации на первом этапе.

## 1. Принципы целевого API

1. **UID из проверенного токена.** Клиент не выбирает владельца записи через uid в JSON. Сервер проверяет Firebase ID token и извлекает UID/логин из подтверждённой identity.
2. **Сервер — источник истины.** Клиент отправляет намерение и необходимые параметры, а не итоговые балансы, рейтинги, награды, права или цену.
3. **Одна бизнес-операция — одна SQL-транзакция.** Списание/начисление валюты, предметы, статус лота, почтовое сообщение, клановый вклад и маркеры получения фиксируются атомарно.
4. **Повтор запроса безопасен.** Для денежных/наградных операций и внешних callback обязательны уникальные operation key / provider order ID и уникальные ограничения в БД.
5. **Чтение ограничено владельцем и страницей.** Не делать публичные полные сканы таблиц. Для лент — cursor pagination, ограничение размера страницы и индексы под фильтр/сортировку.
6. **Публичные проекции отделены от приватных данных.** Рейтинг/публичный профиль не должен раскрывать сохранение, кошелёк, приватные настройки или переписку.
7. **События и realtime отделены от записи.** Сначала фиксируется транзакция, затем событие публикуется через transactional outbox. Потерянное WebSocket-соединение не должно терять саму игровую операцию.
8. **Ошибки имеют стабильные коды.** Минимум: `AUTH_REQUIRED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `STALE_SAVE`, `INSUFFICIENT_FUNDS`, `VALIDATION_ERROR`, `RATE_LIMITED`, `INTERNAL`.

## 3. Контракт /api/save

**Запрос (совместимость на первом переходном этапе):** текущий формат сохранения, включая сессионные маркеры. На новом API не принимать UID как источник полномочий.

**Проверки на сервере:**
- валидный Firebase ID token и соответствие аккаунта;
- размер/структура JSON, допустимые предметы и вместимость инвентаря;
- stale-save / session guard: старая вкладка не перезаписывает более новую сессию;
- ограничение уровня, очков характеристик, серебра и серверных рейтинговых полей;
- поля наград `_aw` забираются максимум один раз;
- результат арены/рейтинга нельзя подтвердить клиентским заявлением.

**SQL-транзакция:** блокировка/версионная проверка строки персонажа → загрузка предыдущего состояния → проверка guard и серверных ограничений → запись сохранения и версии → обновление `player_profiles` из разрешённых публичных полей → запись аудита/outbox при необходимости.

**Ответ:** сохранить существующие поля ответа (включая корректировки/признак stale), пока клиенты не переведены на новую версию. После совместимого периода можно перейти на компактный ответ `{ ok, version, corrections }`.

## 4. Контракт /api/op

Это существующий маршрут. Точные имена операций следует брать из фактических ветвей обработчика; перечисленные ниже действия — бизнес-контракты, подтверждённые текущим кодом.

| Действие | Входное намерение | Атомарные изменения | Обязательные проверки |
|---|---|---|---|
| Выставить предмет на рынок (`mklist`) | ID предмета и цена | Удалить предмет из инвентаря + создать listing | Владелец предмета, допустимая цена, лимит лотов |
| Снять лот (`mkcancel`) | ID лота | Проверить listing + вернуть предмет + закрыть/удалить listing | Только продавец; лот ещё активен |
| Передать предмет письмом (`give`) | Получатель и предмет | Удалить предмет + списать комиссию 1 золото + ledger + создать письмо | Владелец предмета, получатель, баланс, лимиты/запретные предметы |
| Забрать предмет (`take`) | ID письма | Добавить предмет в инвентарь + отметить письмо полученным | Получатель — текущий UID; письмо ещё не забрано; есть место |
| Внести вклад в клан (`donate`) | Тип и сумма ресурса | Списать серебро/железо + увеличить вклад участника/казну | Состоит в клане, положительная сумма, достаточный баланс |

**Важно:** идентификаторы операций и предметов должны быть идемпотентны. Повторная отправка после тайм-аута не должна создать второй лот, второе письмо, второй вклад или второе списание. В PostgreSQL это обеспечивается уникальным `operation_id` и проверкой результата внутри транзакции.

## 5. Кошелёк золота

Существующая функция принимает POST с `a` и параметрами операции. Сохранить смысл следующих действий:

- `get`: получить свой баланс; при первом обращении выполнить одноразовый перенос старого золота из сохранения только для аккаунтов, созданных до даты отсечения 30.10.2026, с действующим ограничением до 1000.
- `pay`: списать золото с проверкой баланса и лимита суммы.
- `xbuy`: обмен серебра на золото с дневным лимитом.
- `gift`: admin-only выдача/списание; положительный подарок может быть отложен в письмо.
- `gclaim`: забрать конкретный подарок ровно один раз.
- `ref`: реферальная награда обеим сторонам ровно один раз после достижения условий.
- `market`: покупка активного лота за золото; списание покупателю, начисление продавцу, передача предмета и закрытие лота атомарны.
- `boss`: награда за допустимую активность с дневными/событийными лимитами и claim key.
- `gsave`, `pwa`, `discord`, `week`: одноразовые награды с проверкой условий аккаунта и маркером получения.

**Целевая модель:** `wallets` — текущий баланс и необходимые счётчики; `wallet_ledger` — неизменяемая история проводок; `wallet_claims` — уникальные ключи получения; `payment_orders` — начисления покупок; все изменения баланса только через единый WalletService. Клиент никогда не обновляет баланс напрямую.

**Legacy bootstrap:** операция должна быть безопасной при гонке двух первых запросов. Использовать уникальную строку кошелька/блокировку и отдельный `legacy_imported_at`; исходное значение сохранять в журнале миграции. Не повторять перенос при повторном запросе.

## 6. Платежи Xsolla

### Создание заказа
Целевой поток: проверить Firebase Auth → проверить SKU по серверному каталогу пакетов → зафиксировать `payment_order` с количеством золота, базовым пакетом и коэффициентом акции → получить Xsolla token → сохранить внешний order ID и статус. Снимок акции в заказе неизменяем: последующее изменение промо не меняет уже созданную покупку.

### Webhook
- Подпись проверяется по исходному телу запроса до JSON-нормализации.
- `user_validation` подтверждает существование аккаунта через identity/profile сервис, а не читает клиентскую запись.
- `order_paid`: сверить order ID, пользователя, SKU/количество и статус заказа; не доверять сумме золота из браузера.
- Уникальный внешний order ID плюс транзакционная проверка гарантируют одно начисление при повторных webhook.
- В одной транзакции создать payment order/claim, увеличить wallet и записать ledger.
- `order_canceled` не должен отменять уже оплаченный/зачисленный заказ; статусы должны иметь разрешённые переходы.
- Секрет webhook хранится только в секретах окружения. Не писать его значение или подпись в логи.

## 7. WebSocket: целевая замена Firestore feeds

Текущий WebSocket использует Firebase token в `hello`, подписки `sub/unsub`, игровые команды рейда/дуэли/мирового цикла/арены и серверные Firestore feeds. Целевой PostgreSQL API должен сохранить клиентский протокол на этапе совместимости, но читать данные из сервисов PostgreSQL и публиковать изменения через outbox/pub-sub.

### Сообщения, уже распознаваемые сервером
| Типы | Домен | Требование к целевому сервису |
|---|---|---|
| `hello` | Идентификация игрока/гостя | Проверка Firebase token; UID только из токена |
| `sub/unsub` | Подписки на feeds | Разрешённый список каналов, лимиты подписок и авторизация приватных каналов |
| `rj/rd/rm/rh` | Рейды | Проверка участника и фазы; награда/урон/ходы — серверные; защита от повторного действия |
| `dj/da` | Дуэли | Проверка участников/хода; один результат раунда; атомарное изменение рейтинга/счёта |
| `wb/wbcl/hunt/war/warc/clan` | Мировой босс, охота, войны, клан | Серверные таймеры, лимиты, claim guards и транзакции |
| `apvp/apa` | Арена против копии героя | Сервер рассчитывает бой и одноразово фиксирует результат |

### Feeds, которые сейчас существуют
`players`, `clans`, `wars`, `world`, `chat`, `terr`, `raidq`.

Целевой контракт feed: начальный snapshot с курсором/версией, затем дельты `upsert/delete`; сортировка и лимиты стабильны. `raidq` нельзя переносить как неограниченную выборку — задать явные фильтр, порядок, TTL и максимальную страницу. Публичные feeds должны отдавать только whitelist полей. Для личных/клановых каналов проверять членство при подписке и повторно при изменении прав.

**Надёжность:** запись в PostgreSQL и событие outbox фиксируются в одной транзакции. Публикация может повториться; клиент/сервер дедуплицирует по event ID и версии сущности.

## 10. Рекомендуемый порядок миграции API

1. Создать PostgreSQL-схему и миграции в отдельной среде; проверить индексы и ограничения на синтетических данных.
2. Реализовать репозитории/сервисы и контрактные тесты без подключения к production.
3. Перенести низкорисковые read-only публичные проекции (например, публичные профили/рейтинги) после тестирования.
4. Перенести отдельные социальные и справочные домены с cursor pagination.
5. Перенести кошелёк/рынок/предметы только после тестов конкурентных запросов, повторов и отката.
6. Перенести игровые транзакции (рейды, дуэли, мировой цикл, арена) с тестами на двойные награды и повторные ходы.
7. Отдельно перенести платежи с тестовыми webhook и проверкой повторной доставки.
8. Выполнить согласованный экспорт и проверку сверки данных; затем согласовать окно «Технические работы» и финальный cutover.
9. Оставить Firebase Auth; отключать Firestore только после периода проверки и явного решения.

## 11. Обязательные тесты до переключения

- stale save: старый клиент не перезаписывает более свежий;
- две одновременные покупки одного лота: успешна максимум одна;
- две одновременные попытки забрать одно письмо/подарок/claim: успешна максимум одна;
- недостаточный баланс: нет частичного списания или предметной передачи;
- повторный Xsolla webhook: золото начисляется ровно один раз;
- отмена после оплаты не откатывает зачисление;
- конкурентный первый вход в кошелёк: legacy balance импортирован ровно один раз;
- повтор одного боевого сообщения/хода: нет повторной награды и рейтинга;
- reconnect WebSocket: snapshot + события после курсора не теряются;
- приватные данные и каналы недоступны посторонним;
- админские операции проверяют роль на сервере и пишут аудит;
- миграционный экспорт сверяется по количеству сущностей, ключевым балансам и контрольным суммам без логирования секретов.

## 12. Открытые решения перед реализацией

1. Оставлять ли инвентарь и экипировку в JSONB сохранения на первом запуске PostgreSQL или сразу нормализовать предметы. Безопасный старт — сохранить текущую структуру JSONB и нормализовать позже после отдельного аудита.
2. Какой именно API-клиентский контракт вводить для новых доменных маршрутов: сохранить Netlify-совместимые пути на переходный период или перейти на единый `/api/v1`.
3. Какой брокер/механизм использовать для outbox → WebSocket при текущем одном серверном процессе; начать можно с PostgreSQL outbox + polling, не добавляя платную инфраструктуру до оценки нагрузки.
4. Где хранить сроки жизни временных боевых состояний и какие события должны быть восстановимы после рестарта сервера.
5. Какая политика хранения/удаления сообщений, логов, push-токенов и антифрод-данных нужна.
